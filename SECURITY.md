# Security Policy

## Supported Versions

This project has not yet reached v1.0. Security fixes are applied to the
`main` branch only. There are no versioned release lines to backport to.

## Trust model

openclaw-bridge is a bridge between two local applications (SillyTavern and OpenClaw). The threat model is a character agent that exceeds its intended authority — either because a malicious message tricks it into doing something it should not, or because the OC configuration grants more capability than the character needs.

### Trust boundaries

```
Internet users / channel participants
        │  (inbound message)
        ▼
  OpenClaw gateway plugin
        │  reads user_id from OC inbound context
        ▼
  ST server plugin  ──── bridge token (Bearer auth) ────
        │  compares user_id to owner_user_ids in character-links.json
        │  injects [OWNER] or [GUEST] label before generation
        ▼
  SillyTavern Generate()
        │  response text + any queued character actions
        ▼
  ST plugin (post-generation)
        │  strips pending actions if sender was [GUEST]
        ▼
  OpenClaw gateway plugin
        │  executes only stripped-clean actions (none for guests)
        ▼
  Channel (Discord, Telegram, …)
```

### What [OWNER] and [GUEST] mean

Every message arrives with a `user_id` in `platform:id` format (e.g. `discord:123456789`). Before calling `Generate()`, the plugin looks up the character's `owner_user_ids` list in `character-links.json`:

- **`[OWNER]`** — the sender is a configured owner. The generated response may include outbound actions (e.g. posting to a channel, writing memory).
- **`[GUEST]`** — everyone else. All `pendingActions` are stripped from the response before it is returned to OC. No outbound action can be triggered by a guest message, regardless of what the LLM generates.

The label is injected by code before generation and cannot be overridden by message content. A guest cannot escalate to owner trust.

### Heartbeat (autonomous generation)

Heartbeat requests arrive with `is_heartbeat: true` and bypass the owner/guest classification entirely — they are generated autonomously on a timer, not in response to any user message. The `[HEARTBEAT]` framing is applied instead, and outbound actions are allowed (the character initiates them, not a user).

## Bridge token

The bridge token is the only authentication mechanism between OC and the ST plugin. Every HTTP call from OC to the plugin must include it as a Bearer token. Without it, endpoints return 401.

- Generated by `setup.sh` as 32 random hex bytes
- Stored in `data/openclaw-bridge/bridge-token.txt` (plugin side) and `~/.openclaw/openclaw-bridge/bridge-token.txt` (OC side), symlinked by `setup.sh` so they stay in sync
- Never stored client-side (no localStorage, no sessionStorage, no cookies)
- The ST extension authenticates over WebSocket to the ST plugin via the same token; the token is only present in the plugin's process memory, not exposed to the browser

If the token is compromised: regenerate with `openssl rand -hex 32 > data/openclaw-bridge/bridge-token.txt`, then update `OPENCLAW_BRIDGE_TOKEN` in each agent's `openclaw.json` and restart OC.

## OpenClaw agent permissions

Out of the box, OC agents can read and write any file your user account can access, execute shell commands, browse the web, send email, and reconfigure OC itself. openclaw-bridge uses OC's `profile: "minimal"` setting to structurally deny all of this at the config layer.

See [OpenClaw security configuration](docs/oc-security.md) for the full hardening guide, including Docker sandboxing, explicit exec deny, AGENTS.md hard blocks, and the complete recommended `openclaw.json` configuration.

**This guide is not exhaustive.** Consult [OpenClaw's own security documentation](https://docs.openclaw.ai/security) for the full picture.

## Known limitations

### No path-based filesystem restrictions in OC

OC's `read` and `write` tools do not currently support path-based access control. With `read` in the allow list, an agent can technically attempt to read any path accessible inside its container. Docker sandbox mode limits what paths are even available — the host filesystem is not mounted — but this relies on Docker isolation rather than OC's own controls.

Do not store sensitive files (SSH keys, API credentials, other characters' tokens) anywhere that could be mounted into an agent's container.

### LLM output is not filtered

The bridge delivers LLM-generated text directly to the channel without content filtering. SillyTavern's own content settings and system prompt instructions are the controls here. If you need profanity filtering, length limits, or topic restrictions, configure them in ST's character card and author's notes.

### Local network assumption

This bridge is designed for a local deployment where ST and OC run on the same machine or private network. Exposing either ST's HTTP API or the WebSocket port (default 8765) to the public internet significantly changes the threat model and is not recommended without additional hardening (TLS, firewall rules, authentication at the reverse-proxy layer).
